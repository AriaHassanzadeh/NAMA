# مرحلهٔ ۱ — ساخت پایهٔ قابل اجرای پروژه

این کار را کامل انجام بده؛ فقط برنامهٔ پیشنهادی ننویس. ابتدا `AGENTS.md`، `docs/PROJECT.md` و `docs/STATUS.md` را بخوان. پاسخ‌ها و توضیح پایان کار فارسی باشند.

## هدف همین مرحله

Next.js، Django و PostgreSQL محلی با Docker Compose بالا بیایند و فرانت از مسیر همان origin وضعیت بک‌اند و اتصال دیتابیس را نشان دهد. طراحی کامل Home و صفحات بعدی مربوط به مرحلهٔ بعد هستند.

## کارها

1. محیط موجود را بررسی کن: سیستم‌عامل، فایل‌های پروژه، وضعیت Git و در دسترس بودن Docker/Compose. اطلاعات حساس را چاپ نکن و تغییرات قبلی کاربر را حفظ کن. اگر Docker نصب نیست یا daemon اجرا نیست، بررسی‌های مستقل را ادامه بده و همان مانع را دقیق گزارش کن؛ از کاربر نخواه secret یا کلید API بفرستد.
2. نسخه‌های سازگار را با مستندات رسمی بررسی و ثبت کن: Next.js پایدار + Node LTS پشتیبانی‌شده، TypeScript/App Router/Tailwind، Python 3.13، آخرین patch امنیتی Django 5.2 LTS، DRF و PostgreSQL. نقطهٔ شروع دیتابیس major 17 است. از Vite استفاده نکن.
3. ساختار سادهٔ `frontend/` و `backend/` را بساز. فرانت npm و lockfile داشته باشد؛ وابستگی‌های پایتون reproducible و pin شده باشند. پوشهٔ دارای مستندات را به‌خاطر خالی نبودن حذف نکن.
4. پیش از اولین migration یک User حداقلی بر اساس `AbstractUser` و `AUTH_USER_MODEL` تنظیم کن. مدل‌های Ads/Products/Shops و فرم ورود را به مراحل خودشان بسپار.
5. Dockerfile مناسب توسعه و `compose.yaml` با سرویس‌های `frontend`، `backend` و `db` بساز. hot reload و volume پایدار دیتابیس داشته باشد. `.env.example` و مراحل تولید تنظیمات محلی را اضافه کن؛ secret واقعی یا نمونهٔ قابل اشتباه با secret تولید را commit نکن. در این مرحله reverse proxy تولید و سرویس پولی لازم نیست.
6. endpoint `GET /api/v1/health/` در Django بساز. واقعاً اتصال دیتابیس را بررسی کند؛ آماده بود پاسخ 200 و در نبود اتصال پاسخ 503 بدهد. اطلاعات اتصال، trace یا secret را در پاسخ نشان ندهد. برای همین رفتار موفق/ناموفق تست متمرکز بنویس.
7. مسیر `/api/v1/` را در Next.js به Django proxy/rewrite کن تا مرورگر به backend داخلی container اشاره نکند. آدرس داخلی در env سمت سرور باشد؛ از `NEXT_PUBLIC_*` برای آن استفاده نکن. برای health عمومی CSRF را خاموش نکن؛ هنگام اضافه شدن درخواست‌های تغییردهنده، session/CSRF حفظ شود.
8. یک صفحهٔ شروع خیلی ساده با `lang="fa"` و `dir="rtl"`، لوگو/فونت محلی و وضعیت واقعی health بساز. حالت pending، موفق و خطا داشته باشد. هنوز دموی HTML را جای برنامه یا داخل iframe نگذار و صفحات کامل را نساز.
9. README اجرای پروژه را با دستورهای واقعی همان scaffold تکمیل کن. اگر `README.md` لازم است بساز و راهنمای فعلی `README-FA.md` را حفظ کن. دستورهای migration، start، stop، logs و checkها را روشن بنویس. دستور حذف volume به‌عنوان stop معمولی نده.
10. بررسی‌های مربوط را اجرا کن: Compose config/build/start، Django check و migrate و تست health، typecheck/lint/build فرانت، و یک درخواست واقعی از مسیر Next به health. در صورت شکست، علت را رفع کن و همان بخش را دوباره بررسی کن. اگر ابزاری در محیط قابل اجرا نبود، آن بررسی را صریحاً «اجرا نشده» ثبت کن.
11. `docs/STATUS.md` را با نتیجهٔ واقعی و قدم بعدی به‌روز کن. Git را در صورت نبود repository مقداردهی کن، اما بدون درخواست کاربر push یا انتشار انجام نده.

## معیار پایان

- سه سرویس قابل راه‌اندازی باشند و دادهٔ دیتابیس بعد از restart باقی بماند.
- مسیر health از origin فرانت کار کند و قطع دیتابیس باعث نمایش خطای واقعی شود.
- بررسی‌های مرتبط پاس شده باشند یا مانع محیطی دقیق ثبت شده باشد.
- تغییرات، روش اجرای پروژه و کار مرحلهٔ بعد واضح باشند.

بعد از جمع‌بندی همین مرحله توقف کن. مرحلهٔ ۲ ساخت پوسته و Home مطابق طراحی مرجع است و با دستور بعدی کاربر شروع می‌شود.
